This guide covers running LM Evaluation Harness and Inspect AI's BFCL benchmark on disconnected clusters where evaluation pods cannot reach the public internet. Both use EvalHub's `test_data_ref` mechanism to make pre-staged assets available under `/test_data`; the framework-specific sections below describe the required layouts. See [Using Custom Data](/guides/custom-data/) for the supported asset sources and the general init-container behavior.

## Prerequisites

- **Model endpoint** (`model.url`) is reachable from inside the cluster — no public internet required.
- **EvalHub job images** (adapter, init container, sidecar) are pullable from your internal registry.
- For the S3 examples in this guide, **MinIO** is reachable from the job namespace. You can use another supported `test_data_ref` source; see [Using Custom Data](/guides/custom-data/).
- **No public internet from evaluation pods.** Pre-stage each selected benchmark's external datasets and support files in the layout its adapter expects. The model endpoint must be reachable from the job, and any asset store used by the init container must be reachable by that container.

## LM Evaluation Harness

### How it works

`lm_eval` normally downloads datasets from Hugging Face at evaluation time. On a disconnected cluster, pre-stage the datasets and tokenizer on a connected machine and make them available to each evaluation pod under `/test_data`.

The init container syncs the configured `test_data_ref` source to `/test_data`. The adapter enables Hugging Face offline mode when it finds both a usable local tokenizer under `/test_data` and a staged dataset bundle containing `dataset_dict.json`. An explicit `parameters.tokenizer` path under `/test_data` is used when supplied. If `parameters.tokenizer` is omitted or blank, the adapter can use the conventional `/test_data/tokenizer` directory when a sibling dataset bundle is detected. An explicit tokenizer value takes precedence over that fallback.

For example, `/test_data/allenai--ai2_arc--ARC-Easy/dataset_dict.json` and `/test_data/tokenizer/` are siblings. Keep the uploaded dataset and tokenizer files in this layout unless you set an explicit local tokenizer path.

### Step 1: Pre-download Datasets

Install the `datasets` library on the connected machine, matching the version used in the adapter image to avoid Arrow compatibility errors:

```bash
pip install "datasets==3.1.0"
```

Download the dataset and save it as an Arrow bundle. The directory name must follow the slug format used by the offline loader:

```python
from datasets import load_dataset, get_dataset_config_names

# Single subset  (e.g. arc_easy)
dataset = load_dataset("allenai/ai2_arc", "ARC-Easy")
dataset.save_to_disk("staging/allenai--ai2_arc--ARC-Easy")
#                              ^^^ slug: dataset_path.replace("/","--") + "--" + subset

# No subset  (e.g. hellaswag)
dataset = load_dataset("hellaswag")
dataset.save_to_disk("staging/hellaswag")
#                              ^^^ slug: dataset_path.replace("/","--")

# Multiple subsets  (e.g. blimp has 67 subsets — download all at once)
for subset in get_dataset_config_names("blimp"):
    load_dataset("blimp", subset).save_to_disk(f"staging/blimp--{subset}")
```

The slug rule in one line:

| Has subset? | Slug formula | Example |
|-------------|-------------|---------|
| Yes | `dataset_path.replace("/","--") + "--" + subset` | `allenai--ai2_arc--ARC-Easy` |
| No | `dataset_path.replace("/","--")` | `hellaswag` |

Examples:

| Benchmark | Dataset Path | Subset | Slug (directory name) |
|-----------|-------------|--------|-----------------------|
| `arc_easy` | `allenai/ai2_arc` | `ARC-Easy` | `allenai--ai2_arc--ARC-Easy` |
| `hellaswag` | `hellaswag` | - | `hellaswag` |
| `blimp` | `blimp` | all subsets (67) | `blimp--<subset>` per subtask |

> `blimp` runs as 67 separate sub-tasks, each backed by a different subset of the `blimp` HuggingFace dataset. Use the multi-subset snippet above (`get_dataset_config_names`) to download them all in one go.

> The full list of benchmark → dataset mappings is in [`docs/dataset-mapping.md`](https://github.com/opendatahub-io/lm-evaluation-harness/blob/incubation/docs/dataset-mapping.md).

### Step 2: Pre-download Tokenizer

On a connected machine, download the tokenizer files:

```bash
pip install huggingface_hub
```

```python
import os
from huggingface_hub import hf_hub_download

repo_id = "meta-llama/Llama-3.1-8B-Instruct"
out_dir = "./staging/tokenizer"
os.makedirs(out_dir, exist_ok=True)

for filename in ["tokenizer.json", "tokenizer_config.json", "special_tokens_map.json"]:
    hf_hub_download(repo_id=repo_id, filename=filename, local_dir=out_dir)
```

Files are saved to `./staging/tokenizer/`. In the pod this maps to `/test_data/tokenizer`.

> Some models use a different tokenizer format and may need additional files — for example `tokenizer.model` (SentencePiece) or `vocab.json` + `merges.txt` (BPE). Adjust the file list to match your model's repository.

### Step 3: Upload to MinIO

Port-forward MinIO and upload the entire `./staging/` directory using the AWS CLI:

```bash
# Export MinIO credentials
export AWS_ACCESS_KEY_ID=<minio-access-key>
export AWS_SECRET_ACCESS_KEY=<minio-secret-key>
export AWS_DEFAULT_REGION=us-east-1

# Port-forward MinIO (replace namespace and pod name as needed)
kubectl port-forward -n minio pod/<minio-pod-name> 9000:9000 &

# Upload staging/ to the offline prefix
aws --endpoint-url http://127.0.0.1:9000 s3 cp ./staging/ s3://mlpipeline/offline/ --recursive
```

Each `staging/<slug>` maps to `s3://mlpipeline/offline/<slug>` — and ultimately to `/test_data/<slug>` in the evaluation pod.

After uploading, the MinIO layout should look like:

```
s3://mlpipeline/offline/
  allenai--ai2_arc--ARC-Easy/   ← dataset bundle
  hellaswag/                    ← dataset bundle
  blimp--adjunct_island/        ← one bundle per blimp subtask
  tokenizer/                    ← tokenizer files
```

### Step 4: Create the MinIO Credentials Secret

The init container uses a Kubernetes Secret to authenticate with MinIO. Create the Secret in the evaluation job namespace before submitting the job:

```bash
kubectl create secret generic minio-credentials \
  --namespace <job-namespace> \
  --from-literal=AWS_ACCESS_KEY_ID=<minio-access-key> \
  --from-literal=AWS_SECRET_ACCESS_KEY=<minio-secret-key> \
  --from-literal=AWS_DEFAULT_REGION=us-east-1 \
  --from-literal=AWS_S3_ENDPOINT=http://<minio-host>:<port>
```

The `secret_ref` value in `test_data_ref.s3` must match this Secret name (`minio-credentials` in the example above). Without this Secret the init container fails before the evaluation runs. See [Using Custom Data](/guides/custom-data/) for the full list of required Secret keys.

### Step 5: Submit an Evaluation Job

Upload the tokenizer directory as `tokenizer/` beside the dataset bundle, then reference the MinIO prefix with `test_data_ref`. With this conventional layout, `parameters.tokenizer` may be omitted or left blank; the adapter uses `/test_data/tokenizer` when it detects the staged dataset. Set `parameters.tokenizer` explicitly to a local path under `/test_data` only when you need a different tokenizer location:

```bash
curl -X POST https://<eval-hub-host>/api/v1/evaluations/jobs \
  -H "Authorization: Bearer <token>" \
  -H "X-Tenant: <namespace>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "arc_easy evaluation",
    "model": {
      "url": "https://my-model.apps.example.com/v1",
      "name": "meta-llama/Llama-3.2-1B-Instruct"
    },
    "benchmarks": [
      {
        "id": "arc_easy",
        "provider_id": "lm_evaluation_harness",
        "test_data_ref": {
          "s3": {
            "bucket": "mlpipeline",
            "key": "offline/",
            "secret_ref": "minio-credentials"
          }
        }
      }
    ]
  }'
```

The init container syncs the entire `offline/` prefix to `/test_data/`, so all datasets and the tokenizer are available at their expected paths. Once the layout is detected, all offline-related environment variables (`HF_HOME`, `HF_DATASETS_OFFLINE`, `HF_HUB_OFFLINE`) are set automatically.

### Multiple benchmarks

EvalHub runs one Kubernetes Job per benchmark. Each benchmark therefore needs its own `test_data_ref`, but they can all point to the same MinIO prefix — upload once to `offline/` and reuse the same ref on every entry. If all benchmarks use the conventional staged tokenizer, omit `parameters.tokenizer`; set an explicit local path only for a benchmark that uses a different tokenizer:

```json
{
  "name": "offline evaluation",
  "model": {
    "url": "https://my-model.apps.example.com/v1",
    "name": "meta-llama/Llama-3.2-1B-Instruct"
  },
  "benchmarks": [
    {
      "id": "arc_easy",
      "provider_id": "lm_evaluation_harness",
      "test_data_ref": { "s3": { "bucket": "mlpipeline", "key": "offline/", "secret_ref": "minio-credentials" } }
    },
    {
      "id": "hellaswag",
      "provider_id": "lm_evaluation_harness",
      "test_data_ref": { "s3": { "bucket": "mlpipeline", "key": "offline/", "secret_ref": "minio-credentials" } }
    }
  ]
}
```

### Troubleshooting

**Init container fails before evaluation starts**

The MinIO credentials Secret is missing or incorrect. Verify it exists in the job namespace and contains `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`, and `AWS_S3_ENDPOINT`.

**Evaluation fails with a network error**

The dataset bundle was not found in MinIO or the slug does not match. The slug is case-sensitive — verify it matches exactly what was uploaded.

**Wrong slug format**

Check [`docs/dataset-mapping.md`](https://github.com/opendatahub-io/lm-evaluation-harness/blob/incubation/docs/dataset-mapping.md) for the correct `dataset_path` and `dataset_name` for your benchmark:

- With subset: `dataset_path.replace("/", "--") + "--" + dataset_name` → `allenai--ai2_arc--ARC-Easy`
- Without subset (Subset column is `-`): `dataset_path.replace("/", "--")` only → `hellaswag`

Only drop the subset suffix when the Subset column in `docs/dataset-mapping.md` is explicitly `-`. If the benchmark has a subset (e.g. `arc_easy` uses `ARC-Easy`), omitting it will produce the wrong slug and the bundle will not be found.

**Offline mode not triggered**

Check that the init container populated `/test_data` with both the tokenizer files under `/test_data/tokenizer` and a dataset bundle beside it containing `dataset_dict.json`. If the tokenizer is stored elsewhere under `/test_data`, set `parameters.tokenizer` to that local path. A Hugging Face tokenizer ID is not a local staged path and does not enable offline mode.

**Tokenizer not found**

For the default tokenizer, verify that the uploaded prefix contains the tokenizer files in `tokenizer/`; they should appear in the pod at `/test_data/tokenizer`. If you set `parameters.tokenizer`, verify that it names the corresponding local path under `/test_data`.

## Inspect AI: BFCL

BFCL (`inspect/bfcl`) downloads its dataset and, for some categories, function implementations and documentation from GitHub. The Hugging Face dataset and tokenizer layout in the previous section does not stage these files. For other Inspect benchmarks that use Hugging Face datasets, follow the Inspect adapter's [Hugging Face asset instructions](https://github.com/eval-hub/eval-hub-contrib/blob/main/adapters/inspect/README.md#huggingface-datasets).

### Stage BFCL assets

Prepare the cache on a connected staging machine using the same `inspect-evals` version as the deployed Inspect adapter. Set `INSPECT_EVALS_CACHE_DIR` to an absolute writable path **before** starting Inspect; the package reads this variable at import time. Run the BFCL task with the same categories that the EvalHub job will use. If the job omits `task_args.categories`, use the task's defaults when warming the cache. For example:

```bash
export INSPECT_EVALS_CACHE_DIR="$PWD/staging/inspect-evals"
inspect eval inspect_evals/bfcl --model mockllm/model --limit 1

# Or warm only the categories selected by the EvalHub job:
inspect eval inspect_evals/bfcl --model mockllm/model --limit 1 -T "categories=['simple_python', 'multiple']"
```

The resulting cache must contain a complete `BFCL/` tree for the selected categories. It includes their question files and applicable ground-truth files. Multi-turn and agentic categories also need the relevant files under `func_source_code/` and `multi_turn_func_doc/`. Copy the entire `BFCL/` directory rather than selecting files manually; the required files are determined by the category manifest in the pinned `inspect-evals` release.

For the MinIO workflow above, upload that directory under a prefix so the pod receives it at `/test_data/BFCL`:

```bash
aws --endpoint-url http://127.0.0.1:9000 s3 sync "$INSPECT_EVALS_CACHE_DIR/BFCL" s3://mlpipeline/bfcl/BFCL
```

Use that prefix in the BFCL benchmark's `test_data_ref`; create the MinIO Secret as described above. For example, when selecting categories explicitly:

```json
{
  "id": "inspect/bfcl",
  "provider_id": "inspect",
  "parameters": {
    "num_examples": 1,
    "task_args": { "categories": ["simple_python", "multiple"] }
  },
  "test_data_ref": {
    "s3": {
      "bucket": "mlpipeline",
      "key": "bfcl/",
      "secret_ref": "minio-credentials"
    }
  }
}
```

The adapter checks the staged data and runtime files needed by the selected categories. When they are complete, it points `INSPECT_EVALS_CACHE_DIR` to `/test_data` and skips the GitHub preflight. If required files are missing, the staged cache is not accepted; with the default `preflight: fail`, the job fails fast when GitHub is unreachable. BFCL categories with additional external-service or snapshot requirements need those dependencies staged or reachable separately; staging the BFCL data tree alone does not make every optional category air-gap compatible. See the [Inspect-Evals BFCL documentation](https://github.com/UKGovernmentBEIS/inspect_evals/tree/main/src/inspect_evals/bfcl) and the [Inspect adapter's disconnected-run notes](https://github.com/eval-hub/eval-hub-contrib/blob/main/adapters/inspect/README.md#huggingface-datasets).
