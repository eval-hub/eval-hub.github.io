---
title: "Using Judge and Scorer Models"
description: "Configure judge, grader, or scorer models and their credentials for EvalHub jobs."
---

Some benchmarks use a second model to judge or score the evaluated model's output. This guide explains how to select that model and configure its connection for Kubernetes evaluation jobs.

The exact parameter name and format are benchmark-specific: a provider may call the model a **judge**, **grader**, or **scorer**. Follow the relevant benchmark documentation for its parameter shape. The Secret and sidecar connection behavior described here is shared by the supported model-authentication flow.

For the sidecar's credential handling details, see [Model Authentication](/guides/model-authentication/). For collection job basics, see [Collections](/guides/collections/).

## Before you start

- Know the target model's endpoint URL and model identifier.
- Know the judge/scorer model identifier and, if it uses a separate connection, its endpoint and API key.
- Have a user or tenant administrator with Secret-creation permission create the Kubernetes Secret in the evaluation's **tenant namespace** before submitting the job. The EvalHub operator does not create per-job judge credential Secrets through the EvalHub custom resource.

The Secret is referenced by name in `model.auth.secret_ref`. **URLs and API keys
for judge, embedding, auditor, or other auxiliary model connections must not appear
in API payload `parameters`.** Put both in the model-auth Secret; keep model IDs
and generation/evaluation settings in parameters. The primary endpoint remains
`model.url`. Keep credentials out of collection definitions and source-controlled
YAML as well.

## Select the judge or scorer model

Set the model identifier in the parameter expected by the benchmark. For example, a collection job can override an empty `judge_model` declared by the collection:

```json
{
  "name": "instruction-output-with-judge",
  "model": {
    "url": "https://target.example/v1",
    "name": "target-model",
    "auth": {
      "secret_ref": "target-and-judge-credentials"
    }
  },
  "collection": {
    "id": "instruction-output-v1",
    "benchmarks": [
      {
        "id": "followbench",
        "provider_id": "followbench",
        "parameters": {
          "judge_model": "judge-model-id"
        }
      }
    ]
  }
}
```

In the UI, provide the judge/scorer identifier in the benchmark field exposed for that job, and select or reference the existing Secret in the model-authentication field. The corresponding API property is `model.auth.secret_ref`; the UI submits that reference but does not create the Kubernetes Secret. If a benchmark uses a different parameter shape—for example, standalone Inspect HLE's `model_roles.grader`—use that provider's instructions instead of assuming `judge_model` is universal.

## Configure the connection Secret

Follow the shared [multi-model Secret setup](/guides/model-authentication/#scenario-4-multi-model-secrets).
Name the Secret `target-and-judge-credentials` to match the request above. For
a separate judge, use `judge_api-key` / `judge_url`; the shared guide defines
the fallback rules, adapter mounts, and sidecar routing behavior.

## Provider-specific configuration

The provider defines the model-selection parameter and the Secret prefix it reads:

| Adapter / use | Model selection in parameters | Secret connection |
|---|---|---|
| [Inspect Petri / Bloom](/adapters/inspect/configuration/) | `auditor_model`, `judge_model`, `scenarios_model`, `realism_model` | Matching `auditor`, `judge`, `scenarios`, `realism` pairs |
| Inspect HLE / CyberSecEval collection judge | `judge_model` | `judge_api-key` / `judge_url` |
| Inspect StrongREJECT | `grader_model` | `judge_api-key` / `judge_url` |
| Inspect named roles, including standalone HLE | `model_roles: {grader: model_id}` or another role name | Matching role pair, e.g. `grader_api-key` / `grader_url` |
| [DeepEval](/adapters/deepeval/configuration/) | `eval_model_name` | `judge_api-key` / `judge_url` |
| FollowBench / ToolEval | `judge_model`, default `model.name` | `judge_api-key` / `judge_url` |
| [IBM CLEAR](/adapters/clear/) | `eval_model_name`, `provider: openai` | `judge_api-key` / `judge_url` |
| [ATIF](/adapters/atif/configuration/) | `model.name` selects the judge | `judge_api-key` / `judge_url`, or the primary connection |
| Promptfoo generation | `generation_provider`, e.g. `openai:chat:generation-model` | `generation_provider_api-key` / `generation_provider_url` |
| Promptfoo grading | `judge_model`, e.g. `openai:chat:judge-model` | `judge_api-key` / `judge_url` |
| [Ragas](/adapters/ragas/configuration/) | `judge_model`, `embedding_model` | Matching `judge` and `embedding` pairs |

Use the shared [role fallback rules](/guides/model-authentication/#scenario-4-multi-model-secrets).
Create the entries needed by the chosen adapter; adding a pair alone does not configure
a model role that the adapter does not read. For custom adapters, use the
[OpenAI-compatible client example](/guides/model-authentication/#openai-compatible-target-judge-and-embedding-clients).

Check the shared [protocol support](/guides/model-authentication/#protocol-support)
before choosing a provider's native client.

Use the model identifier expected by the judge endpoint. A valid Secret and URL do not guarantee that the endpoint hosts a model with that identifier.

## Troubleshooting

- **Missing or invalid Secret:** check that `secret_ref` names a Secret in the job's tenant namespace and that its keys are spelled exactly as documented.
- **Judge authentication failure:** verify `judge_api-key` is present when using a separate judge key; do not put the key in benchmark parameters.
- **Judge endpoint or model not found:** verify `judge_url` and the model identifier. A 404 from the upstream usually means the configured endpoint does not serve that model name.
- **Unexpected target credentials used:** if judge-specific keys are absent, the judge intentionally reuses the target connection.
- **Embedding call returns 404:** a chat endpoint might not implement `/v1/embeddings`. Put the embedding endpoint/key in `embedding_url` / `embedding_api-key` in the Secret and select its model with `embedding_model`.
- **Parameter changes have no effect:** connection URLs/keys in parameters are ignored by the migrated adapters. Update the Secret, then submit a new job.
