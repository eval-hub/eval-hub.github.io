Disconnected Cluster Evaluation

This guide explains how to stage benchmark data for disconnected evaluation. EvalHub’s init container copies each benchmark’s test_data_ref bundle to /test_data; the adapter then reads files from the paths its framework expects. The instructions cover the nine curated collections and 24 benchmark entries in the matrix below.

Prerequisites

Section titled “Prerequisites”
  • Target and judge endpoints must be reachable from the evaluation namespace. Disconnected evaluation still sends inference requests to these services.
  • Adapter, init-container, and sidecar images must be available from a registry reachable by the cluster.
  • Staged assets must be reachable by the init container from the job namespace. Use an internal S3-compatible store such as MinIO, or a PVC that already contains the files.
  • Stage assets while connected. The staging workstation or preparation environment may need Internet access and Hugging Face access. The evaluation pod itself does not need public Internet.
  • A test_data_ref.hf or test_data_ref.git source is fetched when the job starts. It is not an offline source unless the referenced service is reachable inside the cluster. Use S3/PVC for a disconnected cluster.

Per-benchmark references and narrow prefixes

Section titled “Per-benchmark references and narrow prefixes”

test_data_ref belongs on each benchmark object, not on the collection or job as a whole. Upload a benchmark’s bundle under its own prefix and reference that prefix from that benchmark. Avoid attaching a single large prefix containing every collection’s assets to every benchmark: the init container would copy unrelated files into each job’s /test_data volume.

For each benchmark, include only its dataset/cache and the tokenizer or other support files that benchmark requires. The path after the S3 prefix becomes the same path under /test_data. Uploading files to object storage is not sufficient: each data-backed benchmark entry must reference its own staged source.

Connected staging versus disconnected evaluation

Section titled “Connected staging versus disconnected evaluation”

Prepare the assets from a connected staging machine or an approved connected preparation environment. Gated Hugging Face credentials are needed only while downloading gated files such as HLE or GPQA; do not put access tokens in job parameters, the uploaded bundle, or MinIO credentials. Once the assets are staged, the evaluation pod must run without public Internet access. It must still be able to reach the configured target model, judge model (if any), and internal asset store used by the init container.

Target and judge connectivity

Section titled “Target and judge connectivity”

Asset staging does not provide an inference endpoint. The target configured by model.url must resolve and accept requests from the job through the sidecar. For HLE, CyberSecEval 2 Prompt Injection, and FollowBench, configure the judge model name in the benchmark’s parameters.judge_model. The target and judge can share the target connection; when a distinct judge connection is required, configure its credential and optional endpoint in the Secret referenced by model.auth.secret_ref (judge_api-key and, when needed, judge_url). Do not put credentials in parameters or the dataset bundle. See Judge and scorer models for the Secret format and routing behavior.

LM Evaluation Harness

Section titled “LM Evaluation Harness”

How it works

Section titled “How it works”

lm_eval normally downloads datasets from Hugging Face at evaluation time. On a disconnected cluster, pre-stage the datasets and tokenizer on a connected machine and make them available to each evaluation pod under /test_data.

The init container syncs the configured test_data_ref source to /test_data. The adapter enables Hugging Face offline mode when it finds both a usable local tokenizer under /test_data and a staged dataset bundle containing dataset_dict.json. An explicit parameters.tokenizer path under /test_data is used when supplied. If parameters.tokenizer is omitted or blank, the adapter can use the conventional /test_data/tokenizer directory when a sibling dataset bundle is detected. An explicit tokenizer value takes precedence over that fallback.

For example, /test_data/allenai--ai2_arc--ARC-Easy/dataset_dict.json and /test_data/tokenizer/ are siblings. Keep the uploaded dataset and tokenizer files in this layout unless you set an explicit local tokenizer path.

Step 2: Pre-download Tokenizer

Section titled “Step 2: Pre-download Tokenizer”

On a connected machine, download the tokenizer files:

Some Hugging Face repositories are gated. Accept the repository’s terms and authenticate on this staging machine with an account that has read access (for example, use hf auth login or provide HF_TOKEN to the download process). The token is only needed to download the files: do not put it in the staging directory or upload it with the assets. A disconnected evaluation should consume the staged files without fetching them from Hugging Face.

Set revision to the tokenizer repository revision paired with the served model; use its full commit SHA for reproducible staging. Do not assume that the model endpoint name identifies this tokenizer revision. This example saves files to ./staging/arc_easy/tokenizer/. In the pod this maps to /test_data/tokenizer. Put the compatible tokenizer in each benchmark bundle that requires it; you can copy the same directory into multiple bundles when those benchmarks use the same tokenizer revision.

The list above is illustrative, not exhaustive. Stage every tokenizer, vocabulary, merge, and configuration file required by the exact tokenizer and revision you evaluate. Check the tokenizer repository and include files such as tokenizer.model (SentencePiece) or vocab.json and merges.txt (BPE) when applicable; the three common files above are not sufficient for every model.

Step 5: Submit an Evaluation Job

Section titled “Step 5: Submit an Evaluation Job”

Upload the tokenizer directory as tokenizer/ beside this benchmark’s dataset bundle, then reference that benchmark-specific MinIO prefix with test_data_ref. With this conventional layout, parameters.tokenizer may be omitted or left blank; the adapter uses /test_data/tokenizer when it detects the staged dataset. Set parameters.tokenizer explicitly to a local path under /test_data only when you need a different tokenizer location:

The init container syncs only the referenced benchmark prefix to /test_data/; the dataset bundle and tokenizer are then available at their expected paths. Once the layout is detected, the adapter sets its Hugging Face cache paths and offline variables automatically, including HF_HOME, HF_HUB_CACHE, HF_DATASETS_CACHE, HF_HUB_OFFLINE, HF_DATASETS_OFFLINE, HF_EVALUATE_OFFLINE, and TRANSFORMERS_OFFLINE.

Section titled “Multiple benchmarks”

Troubleshooting

Section titled “Troubleshooting”

Init container fails before evaluation starts

The MinIO credentials Secret is missing or incorrect. Verify it exists in the job namespace and contains AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_DEFAULT_REGION, and AWS_S3_ENDPOINT.

Evaluation fails with a network error

The dataset bundle was not found in MinIO or the slug does not match. The slug is case-sensitive — verify it matches exactly what was uploaded.

Wrong slug format

Use docs/dataset-mapping.md as a starting point, then verify dataset_path and dataset_name against the task configuration in the exact adapter revision deployed in your cluster. The linked mapping follows a moving branch and can differ from the downstream adapter. For crows_pairs_english in the RHOAI adapter revision linked above, the values are jannalu/crows_pairs_multilingual and english, producing the slug jannalu--crows_pairs_multilingual--english.

  • With subset: dataset_path.replace("/", "--") + "--" + dataset_name → allenai--ai2_arc--ARC-Easy
  • Without a subset configured by the deployed task: dataset_path.replace("/", "--") only → hellaswag

Omit the subset suffix only when the deployed task configuration has no dataset subset. The linked mapping is a reference and may differ from the downstream adapter; do not use a - in that moving mapping to override the deployed task configuration. If the task config defines a subset (for example, arc_easy uses ARC-Easy), include it in the slug or the bundle will not be found.

Offline mode not triggered

Check that the init container populated /test_data with both the tokenizer files under /test_data/tokenizer and a dataset bundle beside it containing dataset_dict.json. If the tokenizer is stored elsewhere under /test_data, set parameters.tokenizer to that local path. A Hugging Face tokenizer ID is not a local staged path and does not enable offline mode.

Tokenizer not found

For the default tokenizer, verify that the uploaded prefix contains the tokenizer files in tokenizer/; they should appear in the pod at /test_data/tokenizer. If you set parameters.tokenizer, verify that it names the corresponding local path under /test_data.

LightEval

Section titled “LightEval”

The disconnected LightEval adapter uses the Hugging Face cache and dataset cache staged by the selected benchmark’s test_data_ref. It also imports tinyBenchmarks.pkl eagerly while loading LightEval task definitions, so this file must be present even when the selected task does not use TinyBenchmarks.

For each LightEval benchmark in the matrix, prepare a separate bundle using the same LightEval adapter image and task configuration as the deployed job. The image does not download NLTK data during its build, and a disconnected job does not download it at runtime. Every LightEval bundle must therefore include NLTK punkt and punkt_tab, even when the benchmark itself does not tokenize sentences. The task registry imports IFEval, which uses those resources. Preserve the cache layout produced by Hugging Face:

The adapter sets its Hugging Face cache variables to the staged paths and disables Hub downloads. It also selects the staged NLTK path and validates it before importing the task registry, using only the staged files rather than an image-level fallback. It mirrors the read-only datasets cache metadata into a writable job cache; keep the staged source intact. Do not include caches for unrelated tasks in the benchmark prefix. The LCB v6, GPQA Diamond, and MATH-500 endpoint jobs in this matrix use the task-specific datasets, tinyBenchmarks.pkl, and NLTK data; they do not require a separate model tokenizer unless the selected model/task configuration uses one. GPQA Diamond may require accepted gated-repository terms and an authenticated token while staging. The token must not be placed in the bundle or the evaluation pod.

To prepare one task cache, use a connected environment with the same LightEval adapter image and task registry as the deployed job. Download NLTK data into the bundle before importing task definitions. Put the pinned tinyBenchmarks.pkl file at the package’s task-registry location before loading task definitions, then run the following from the adapter’s application directory. Repeat with a fresh bundle directory and the exact task ID for each LightEval benchmark:

Authenticate to gated Hugging Face repositories before this step. Do not print HF_TOKEN; keep it in the connected staging shell or a protected staging Secret, and never upload it with the bundle. Upload the resulting hub/, datasets/, lighteval/tinyBenchmarks.pkl, and complete nltk_data/tokenizers/punkt/ and punkt_tab/ directories under each LightEval benchmark’s prefix. Include tokenizer/ only if the model/task configuration requires a local model tokenizer. The adapter sets NLTK_DATA automatically when it finds the staged directory in /test_data.

Use the test_data_ref prefix from the matrix on each LightEval benchmark entry. For example:

tinyBenchmarks.pkl is an auxiliary framework asset, not a dataset that can be omitted based on the selected benchmark. Include the exact file required by the LightEval version in the deployed adapter image. If it is missing, LightEval may try to fetch it during import despite Hugging Face offline flags.

If punkt or punkt_tab is missing, empty, or incomplete, the adapter fails before loading the LightEval task registry with an error naming /test_data/nltk_data/tokenizers. Verify that punkt/english.pickle is non-empty and that punkt_tab/english/ contains the files from the same NLTK version used in the deployed image. An empty directory does not satisfy this check, even if NLTK data happens to exist elsewhere in the image. Re-stage the affected benchmark bundle and rerun its job; the disconnected evaluation pod will not attempt a download.

Inspect AI: Hugging Face datasets and CyberSecEval 2

Section titled “Inspect AI: Hugging Face datasets and CyberSecEval 2”

Inspect HLE and DocVQA use Hugging Face-backed datasets; CyberSecEval 2 Prompt Injection uses a pinned JSON file fetched from GitHub in connected mode. For offline runs, the corresponding Inspect adapter image must include the staged-cache support and the benchmark’s own test_data_ref.

HLE

Section titled “HLE”

Stage the pinned cais/hle dataset revision using an authenticated Hugging Face account that has access to the gated repository. Keep the generated Hugging Face cache layout together (including datasets/, hub/, and any referenced Xet files) under the benchmark’s S3 prefix. Access credentials are needed only during connected staging. The evaluation job still needs a reachable target and a reachable judge. Configure the judge model with the benchmark’s judge_model parameter and put any judge endpoint/key settings in the Secret referenced by model.auth.secret_ref; see Judge and scorer models.

DocVQA

Section titled “DocVQA”

Stage the pinned lmms-lab-encoder/DocVQA DocVQA configuration and its validation split. Preserve the complete cache, including the image bytes/blobs referenced by the dataset records; a metadata-only dataset snapshot is insufficient. Keep the original Hugging Face cache layout under the benchmark prefix and include any Xet-backed objects created by the staging client. The target endpoint must be reachable inside the cluster and must accept image inputs.

Inspect AI: BFCL

Section titled “Inspect AI: BFCL”

BFCL (inspect/bfcl) downloads its dataset and, for some categories, function implementations and documentation from GitHub. The Hugging Face dataset and tokenizer layout in the previous section does not stage these files. For other Inspect benchmarks that use Hugging Face datasets, follow the Inspect adapter’s Hugging Face asset instructions.

Also include every selected category’s question file and applicable ground-truth file. Multi-turn and agentic categories need their corresponding files under func_source_code/ and multi_turn_func_doc/. Copy the entire BFCL/ directory rather than selecting files manually; the required paths are determined by the category manifest in the pinned inspect-evals release.
